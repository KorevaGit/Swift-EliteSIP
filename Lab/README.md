# Лабораторный Asterisk

Локальный Asterisk для отладки EliteSIP. Держит `chan_sip`, потому что боевой
сервер настроен на него.

Три стенда. Первые два — с общими руками написанными конфигами, третий живёт
своей жизнью:

| Стенд | Версия | SIP UDP | SIP TLS | Зачем |
|---|---|---|---|---|
| `docker-compose.13.yml` | Asterisk 13.38.3 из исходников | 5070 | 5071 | **точная боевая версия**, основная для проверок клиента |
| `docker-compose.yml` | Asterisk 16.28 из пакета Debian | 5060 | 5061 | быстро поднимается, полезна для сравнения поведения версий |
| `docker-compose.freepbx.yml` | FreePBX 15 поверх того же Asterisk 13.38.3 | 5080 | 5081 | учебный стенд, чтобы понимать боевой сервер — см. [FREEPBX.md](FREEPBX.md) |

Asterisk 13 приходится собирать из исходников: в пакетах его нет (bullseye даёт
16, stretch с 13.14 уже в архиве), а отлаживать сигнализацию против другой
мажорной версии — значит ловить чужие баги. Сборка занимает несколько минут и
проверяет наличие `chan_sip.so` и `res_srtp.so` до того, как образ будет готов.

## Запуск

```bash
./certs/generate.sh && docker compose -f docker-compose.13.yml up -d
```

```bash
./certs/generate.sh && docker compose up -d
```

Проверка:

```bash
docker exec elitesip-lab asterisk -rx 'sip show peers'
```

## Что внутри

**Asterisk 16 LTS на Debian bullseye.** Версия выбрана не случайно: с 17-й
`chan_sip` помечен deprecated и не собирается по умолчанию, а в 21-й удалён.
Отлаживаться надо против того же драйвера, что на бою. Dockerfile проверяет
наличие `chan_sip.so` на этапе сборки, чтобы проблема не всплыла в рантайме.

**Пиры**

| Номер | Пароль | Транспорт | Шифрование |
|---|---|---|---|
| 100, 101, 102 | `elite100` … | UDP 5060 | нет |
| 200 | `elite200` | TLS 5061 | SRTP обязателен |

Два профиля вместо одного переключателя: в `chan_sip` параметр `encryption=yes`
означает строго шифрованно, промежуточного «optimistic» там нет. Открытый UDP
нужен на этапах M1–M2, потому что такой трафик читается в Wireshark, и это
экономит часы отладки.

**Тестовые номера**

| Номер | Что делает |
|---|---|
| 600 | эхо — слышно себя, значит RTP ходит в обе стороны |
| 601 | проигрывает файл — отделяет «не работает приём» от «не работает передача» |
| 602 | тон 1004 Гц — для джиттер-буфера и искажений |
| 603 | принимает DTMF и произносит обратно — проверка RFC 2833 |
| 700 | эхо **за мостом** — цель для перевода |
| 701 | тон 1004 Гц за мостом — второй участник перевода |
| 702 | приветствие за мостом — третий участник |
| 8000 | конференция ConfBridge, `80XX` — комната с номером `XX` |
| 100–102, 200 | звонок другому пиру |
| 22998 | заглушка «горячей раздачи» |

**Переводить можно только то, у чего есть собеседник.** Канал внутри
приложения (600, 602, 22998) разговаривает с `Echo()` или `Playback()`, а не с
другим каналом; на REFER по такому каналу Asterisk 13 отвечает NOTIFY с
`503 Service Unavailable` — и на слепой перевод, и на консультационный с
Replaces. Со стороны клиента это выглядит как «сервер не умеет переводить»,
хотя умеет. Поэтому цели перевода — 700, 701 и 702: они уводят звонок в
`Local`-канал, и наша нога оказывается в настоящем мосту. Дозвон обратно на
зарегистрированный softphone для этого не годится: на Docker Desktop внешний
порт клиента меняется чуть ли не на каждой датаграмме, и INVITE от Asterisk
уходит на устаревшую привязку — проверено, `408 Request Timeout`.

## Сеть на macOS

Docker Desktop держит контейнер за NAT, и его адрес `172.17.x.x` с хоста
недостижим. Поэтому:

* порты публикуются наружу: 5060/udp, 5061/tcp, 10000–10030/udp
  (диапазон RTP в `rtp.conf` совпадает с публикацией — при расширении править
  оба места);
* в `sip.conf` стоит `externaddr` с адресом Mac в локальной сети — его
  подставляет `lab.sh` при каждом запуске;
* `localnet=127.0.0.0/8` — диапазон, в который заведомо не попадает ни один
  пир. Это не описка, разбор ниже.

### Почему localnet объявлен «пустым» диапазоном

Место, на котором потеряли время дважды, поэтому записано подробно.

**Все пиры приходят с одного адреса.** Docker Desktop переписывает адрес
источника: и клиент на самом Mac, и телефон в локальной сети видны Asterisk как
шлюз `172.20.0.1`. В `sip show peers` у всех стоит он. Значит разделить их по
адресу нельзя в принципе.

**Прежнее `localnet=172.16.0.0/12` этот шлюз накрывало.** Asterisk считал всех
локальными и клал в SDP свой `172.20.0.2` — адрес, до которого с macOS маршрута
нет. Симптом обманчивый: регистрация проходит, звонок устанавливается, ACK
уходит, и только звука нет ни в одну сторону, а через несколько секунд линия
рвётся. Выглядит как поломка аудиотракта, хотя это одна строка в SDP.

**Убрать `localnet` совсем — не решение**, хотя напрашивается первым. `chan_sip`
включает подстановку `externaddr` только при непустом списке; без него
`sip show settings` пишет «SIP address remapping: Disabled, no localnet list», и
в SDP снова уходит внутренний адрес. Проверено на живом Asterisk — вышло именно
так.

Поэтому список непустой, но заведомо ни с чем не совпадающий: он нужен, чтобы
включить подстановку, а не чтобы кого-то пометить локальным. Проверка, что всё
на месте:

```bash
docker exec elitesip-lab13 asterisk -rx 'sip show settings' | grep -A5 'Network Settings'
```

Должно быть `SIP address remapping: Enabled using externaddr`. Если написано
`Disabled` — вернулась та самая тишина.

## Проверка клиента против лабы

```bash
cd Tools/sipcheck && swift run sipcheck --user 100 --password elite100 --transport udp --port 5070 --duration 10
```

```bash
cd Tools/sipcheck && swift run sipcheck --user 200 --password elite200 --transport tls --port 5071 --insecure-tls --duration 10
```

Звонок с прогоном RTP на эхо-тест:

```bash
cd Tools/sipcheck && swift run sipcheck --user 100 --password elite100 --transport udp --port 5070 --call 600 --duration 6
```

Микрофон при этом не задействован: у консольной программы нет бандла, а значит и
разрешения на него. Проверяется всё остальное — INVITE, согласование SDP, ACK,
встречный поток RTP и BYE. «Слышно себя» проверяется только в приложении.

Порты 5070/5071 — это Asterisk 13, боевая версия. Для лабы на 16 подставить
5060/5061.

## Почему RTP-порты публикуются один в один

SIP-порты у лаб разные (5060 и 5070), а диапазон RTP у обеих — `10000-10030`,
и публикуется он **без сдвига**. Сдвинуть его нельзя: Asterisk объявляет в SDP
свой внутренний номер порта, клиент отправляет медиа именно туда, и при
изменённой публикации попадает в пустоту.

Ошибка при этом выглядит обманчиво: сигнализация отрабатывает полностью, звонок
успешно устанавливается и завершается, а звука просто нет. Проверять надо со
стороны сервера:

```bash
docker exec elitesip-lab13 asterisk -rx 'sip show channelstats'
```

Нули в колонке `Recv` означают, что до Asterisk не дошло ни одного пакета.

Следствие: **две основные лабы Asterisk не могут работать одновременно** — они
спорят за эти порты. Стенд FreePBX использует отдельный диапазон
`10200–10230`, тоже опубликованный один в один, поэтому может работать рядом с
одной из них и пригоден для end-to-end проверки RTP и записей разговоров.

Юнит-тесты проверяют логику, а совместимость с `chan_sip` — только живой сервер.
`sipcheck` показывает весь обмен и код каждого ответа, без интерфейса.

Флаг `--insecure-tls` отключает проверку сертификата и нужен здесь только из-за
самоподписанного сертификата лабы. Без него клиент корректно отказывается
подключаться — это проверено.

## Странности vpnkit, о которых стоит знать

Docker Desktop на macOS переназначает внешний UDP-порт довольно свободно: за
75-секундный прогон Asterisk сообщал в `rport` то один порт, то другой, хотя
локальный порт клиента не менялся. Для реального NAT это нетипично, но клиент
из-за этого правит Contact не более одного раза за попытку регистрации — иначе
получался бы круг «исправили Contact, сервер видит новый порт».

## Ограничения

`features.conf` лабы переведён на подтверждённые боевые коды builtin-фич
(`##` blindxfer, `*02` atxfer, `**` disconnect); код конференции (`*3`)
остаётся лабораторным прототипом — на бою такой dynamic-фичи не нашлось
вообще. Разбор — комментарии в самом файле и таблица ниже.

## Боевые фич-коды: что подтвердилось, а что нет

30 июля 2026 пришёл вывод `core show features` с боевого сервера:

| Feature | Default | Боевой | Догадка лабы |
|---|---|---|---|
| Pickup | `*8` | `*8` | не переопределён |
| Blind Transfer | `#` | `##` | `*0` |
| Attended Transfer | (нет) | `*02` | `*2` |
| Disconnect Call | `*` | `**` | `*9` |
| apprecord (dynamic) | нет | `*1` | не воспроизведён |
| cancel-transfer (dynamic) | нет | `*77` | не воспроизведён |

Ни один builtin-код из лабы не совпал с боевым буквально — коды в лабе
обновлены под боевые. Для клиента это не критично: перевод (M5) идёт через
SIP REFER, а не через эти DTMF-коды.

`apprecord` частично прояснилась 31 июля 2026: боевой `sip show peer`
показал у тестового пира `Record On/Off feature: apprecord` — это штатный
peer-level переключатель записи (`recordonfeature`/`recordofffeature`), и *1
просто его дёргает. Что конкретно фича делает внутри `[applicationmap]`
(вызывает `MixMonitor` напрямую или что-то ещё), всё ещё не видно —
`core show features` печатает код и имя, не тело.

Важнее другое: **конференции (dynamic feature вроде `conf_pull`) в этом
списке нет вообще.** `core show features` печатает весь `[applicationmap]`
безусловно, а не только активные на звонке фичи — значит на боевом сервере
такой записи либо нет, либо конференция агенту доступна не через эту DTMF-фичу.
Настраиваемый код `*3` в настройках EliteSIP (по умолчанию — тот же символ, что
в лабе) остаётся непроверенной догадкой, а не подтверждённым боевым значением;
подробнее — [conference.md](../docs/conference.md). Код `*022998#` из
[FREEPBX.md](FREEPBX.md) тоже не входит ни в builtin, ни в dynamic список —
похоже, это не feature-код вообще, а отдельный контекст/макрос в
`extensions_custom.conf`.

Присланного вывода не заменяет сам `features.conf`: коды видны, а привязка к
диалплану (какой канал, какой контекст, что делает `*022998#` целиком) — нет.
Как и раньше: пришлите боевой `features.conf` и релевантный `extensions.conf` —
заменю догадки один в один.
