# FreePBX в паре с Asterisk

Учебный стенд. Не нужен для разработки клиента — нужен, чтобы понимать, что
происходит на боевом сервере.

```bash
docker compose -f docker-compose.freepbx.yml up -d
```

Веб-интерфейс: <http://localhost:8080>. Интерфейс по умолчанию **на русском**.
При первом входе FreePBX попросит создать учётку администратора — она локальная,
к SIP отношения не имеет.

| | |
|---|---|
| FreePBX | 15 (штатно работает с Asterisk 13 — та же пара, что на бою) |
| Asterisk | 13.38.3, тот же образ, что в лабе для отладки клиента |
| SIP | UDP 5080, TLS 5081 (свои порты, чтобы не спорить с лабами) |
| Веб | 8080, язык `ru_RU` |
| CDR и CEL | пишутся в базу через ODBC — работают |

## Готовые номера

Стенд поднимается сразу с восемью внутренними номерами (`chan_sip`, как на бою).
Имена повторяют боевые, чтобы отчёты выглядели узнаваемо. Список —
[freepbx/extensions.csv](freepbx/extensions.csv), пароль у каждого вида
`elite<номер>`.

| Номер | Имя |
|---|---|
| 100–103 | Agent 100…103 |
| 634 | Poluhina_Anna |
| 711 | Call_Center |
| 724 | Call Center udalen |
| 807 | Yartseva_Elena |

Импорт сделан штатным механизмом FreePBX — модулем Bulk Handler
(`fwconsole bulkimport ... --type=extensions`), а не записью в базу напрямую.

## Как наполнить CDR

Страница «Отчёты → CDR» пуста, пока не было ни одного звонка, и понять по ней
ничего нельзя. Клиента, который умеет звонить, ещё нет — это M2. Поэтому звонки
инициирует сам Asterisk:

```bash
./freepbx-traffic.sh
```

Скрипт делает несколько звонков на эхо-тест `*43` (отвечает сразу — получаются
записи ANSWERED) и один на незарегистрированный 711 (уходит в `macro-vm` по
CHANUNAVAIL — ровно так же выглядит недоступный агент на бою), после чего
показывает получившиеся CDR и цепочку CEL. Есть режимы `show` и `clear`.

## Что такое FreePBX

Три вещи в одной, и путаница между ними — источник большинства недоразумений:

1. **База данных** (`asterisk` в MariaDB), где лежат пиры, очереди, маршруты.
2. **Генератор конфигов**: по нажатию «Apply Config» FreePBX выгружает базу в
   обычные текстовые файлы `/etc/asterisk/*.conf` и говорит Asterisk перечитать
   их.
3. **Набор готового диалплана** — контексты и подпрограммы (`from-internal`,
   `sub-record-check`, `macro-dial-one`), которые генерируются всегда.

**Asterisk про FreePBX не знает ничего.** Он читает файлы. Всё «управление» —
это генерация файлов плюс `reload`. Отсюда главное практическое следствие:
править `/etc/asterisk/*_additional.conf` руками бесполезно, следующий «Apply
Config» их перезапишет.

## Карта файлов

| Файл | Кто пишет | Можно ли править руками |
|---|---|---|
| `sip.conf`, `extensions.conf`, `features.conf` | модуль `core`, это **символические ссылки** | нет, там только `#include` |
| `*_additional.conf` | FreePBX при каждом Apply Config | **нет**, перезапишется |
| `*_custom.conf` | вы | **да**, FreePBX их не трогает никогда |

Первая строка неочевидна и хорошо объясняет устройство. В `/etc/asterisk` десять
файлов — не файлы, а ссылки:

```
/etc/asterisk/sip.conf -> /var/www/html/admin/modules/core/etc/sip.conf
```

То есть точки входа принадлежат модулю FreePBX, а не системе. Они статические,
в них только `#include`, и меняются они только при обновлении модуля. Всё
изменяемое лежит в подключаемых файлах.

Посмотреть точки входа и полный список:

```bash
./freepbx-inspect.sh
```

## Как увидеть связку своими глазами

Смысл стенда именно в этом: изменить что-то в интерфейсе и посмотреть, какие
файлы от этого поменялись.

```bash
./freepbx-inspect.sh snapshot до
```

Дальше в интерфейсе: **Applications → Extensions → Add New Chan_SIP Extension**,
номер 711, секрет любой, «Submit», затем «Apply Config».

```bash
./freepbx-inspect.sh snapshot после
./freepbx-inspect.sh diff до после
```

В диффе будет видно, что появился пир в `sip_additional.conf` и записи в
`extensions_additional.conf`. Дальше тем же способом стоит посмотреть, что
добавляет очередь (**Applications → Queues**, номер 2929, участник 711) и что
добавляет включение записи разговоров у номера.

## Разбор боевого звонка

Это тот самый CEL, который ты присылал, по шагам. Он объясняет всю схему
горячей раздачи.

```
1:06:20  CHAN_START   from-trunk         SIP/21241725864408-0003b86f
1:06:39  ANSWER       from-trunk         AutoDialer
1:06:39  APP_START    from-auto-dialer   Dial   расш 79275171869
1:06:39  CHAN_START   from-internal      Local/2929@from-internal-000124d0;1
1:06:39  CHAN_START   from-internal      Local/2929@from-internal-000124d0;2
1:06:39  APP_START    sub-record-check   MixMonitor   Local/…;2
1:06:39  APP_START    from-internal      Queue        Local/…;2
1:07:24  CHAN_START   from-internal      SIP/711-0003b88a     расш 2929
1:07:25  ANSWER       from-internal      AppQueue     SIP/711
1:07:25  BRIDGE_ENTER SIP/711  ↔  Local/…;2
1:07:31  HANGUP / CHAN_END / LINKEDID_END
```

Что здесь происходит:

1. **Канал от провайдера** (`from-trunk`) — это плечо к клиенту. Автодозвон
   набрал `79275171869`, клиент ответил через 19 секунд.
2. **Пара Local-каналов** `;1` и `;2` — ключевой механизм. `Local/2929@from-internal`
   создаёт два связанных псевдоканала: `;1` — тот, с которым разговаривает
   вызывающая сторона, `;2` — тот, который **исполняет диалплан** по адресу
   `2929@from-internal`. Так звонок попадает в очередь не напрямую, а через
   диалплан, и по дороге подхватывает всё, что диалплан делает.
3. **`sub-record-check` → `MixMonitor`** — это и есть «по дороге». Подпрограмма
   FreePBX решает, надо ли записывать, и включает запись. Запись целиком на
   стороне сервера: клиент про неё не знает и ничего для неё не делает.
4. **`Queue`** на `;2` — звонок встал в очередь 2929 и ждал 45 секунд.
5. **Очередь позвонила агенту**: `SIP/711` с `расш 2929`. Агент ответил через
   секунду, каналы соединились в мост.

### Что из этого важно для клиента

**Агент видит номер очереди, а не клиента.** В CDR у плеча очереди «Имя
звонящего» — `"AutoDialer" <2929>`. Номер клиента `79275171869` живёт в
`accountcode` (колонка «Учётка») и в SIP-сообщениях агенту не приходит. Значит
окно входящего вызова может честно показать «раздача из 2929», но не клиента.
Чтобы показать клиента, диалплан должен передать его номер — например через
`Set(CALLERID(...))` перед звонком агенту или отдельным SIP-заголовком.

### Что на бою НЕ от FreePBX

Стандартный FreePBX создаёт `from-trunk`, `from-internal`, `from-did-direct`,
`from-pstn` и подпрограммы `sub-*`. Контекста **`from-auto-dialer` в стандартной
поставке нет** — это дописанный на боевом сервере диалплан. Там же, скорее
всего, живут и `accountcode` с номером клиента, и «Пользовательское поле» с
идентификатором лида, и коды `*022998#` и `*3`.

Практический вывод: коды, которые мы восстановили в лабе по догадке, надо искать
не в настройках FreePBX, а в `extensions_custom.conf` и `features.conf` боевого
сервера — то есть в файлах, которые FreePBX не генерирует.

## Что проверено на стенде

Все контексты, которые видны в боевых CDR и CEL, FreePBX создаёт сам и они здесь
есть: `from-internal`, `from-trunk`, `from-pstn`, `from-did-direct`,
`sub-record-check`, `macro-dial-one`. Всего 110 контекстов. Логика
`sub-record-check` совпадает с боевой: она читает из внутренней базы Asterisk
(`DB(AMPUSER/…/recording/…)`), решает, надо ли записывать, и включает
`MixMonitor`.

Единственное, чего в стандартной поставке нет — **`from-auto-dialer`**. Значит на
бою это дописанный диалплан, и коды `*022998#` с `*3` надо искать там же.

## Как устроена запись CDR и CEL

Цепочка длинная, и рвётся она обычно молча — конфиги выглядят правильными, а
таблицы остаются пустыми:

```
cdr_adaptive_odbc / cel_odbc   (модули Asterisk)
  -> res_odbc                  соединение asteriskcdrdb
  -> unixODBC                  DSN MySQL-asteriskcdrdb из /etc/odbc.ini
  -> драйвер MariaDB ODBC      libmaodbc.so
  -> база asteriskcdrdb        таблицы cdr и cel
```

Проверять надо по звеньям, а не целиком:

```bash
docker exec elitesip-freepbx asterisk -rx 'odbc show all'          # видит ли Asterisk соединение
docker exec elitesip-freepbx isql -v MySQL-asteriskcdrdb freepbxuser freepbxpass   # работает ли драйвер
docker exec elitesip-freepbx mysql -e 'SELECT COUNT(*) FROM cdr' asteriskcdrdb
```

Таблицу `cel` FreePBX не создаёт — она заводится нашим
[freepbx/cel.sql](freepbx/cel.sql). Файлов `cel.conf` и `cel_odbc.conf` он тоже
не генерирует, они наши: без `enable=yes` в `cel.conf` журнал событий не ведётся
вообще, каким бы полным ни был список событий.

## Что пришлось починить для Debian

FreePBX официально ставится на свой дистрибутив, поэтому на чистом Debian
понадобились шесть правок. Записаны, чтобы не искать заново:

1. **`gnupg`** — FreePBX проверяет подписи модулей через `gpg`, и без него
   установка падает с «Could not find gpg command!». С `--no-install-recommends`
   пакет не приезжает сам.
2. **Патч PHP 7.4** ([freepbx/patch-php74.sh](freepbx/patch-php74.sh)) — код
   FreePBX 15 писался под PHP 5–7.2 и использует `$s{0}` для смещений в строках
   и `implode($array, 'glue')` со старым порядком аргументов. В 7.4 и то и другое
   deprecated, а обработчик ошибок Symfony превращает предупреждение в
   исключение: команда падает там, где по сути всё сработало. Настройки
   `error_reporting` не помогают — обработчик регистрируется раньше.

   Патч вызывается **после каждой установки модулей**, а не один раз: `install`
   и каждый `ma install` перезаписывают уже исправленные файлы своими свежими
   копиями. Именно на этом сборка ломалась дважды.
3. **`fwconsole ma install cdr` отдельной командой** — `installall` оставляет
   модуль `cdr` в состоянии «отключён, ожидает обновления», а
   `res_odbc_additional.conf` с описанием подключения к базе пишет именно он.
   Без этого шага соединения `asteriskcdrdb` в Asterisk нет, и CDR с CEL молча
   никуда не пишутся.
4. **Драйвер MariaDB ODBC из исходников** — готового пакета нет ни в bullseye
   (`odbc-mariadb` появился только в bookworm), ни в репозитории MariaDB под
   arm64. Плюс `unixodbc-dev` нужен на этапе `configure` самого Asterisk, иначе
   `res_odbc`, `cdr_adaptive_odbc` и `cel_odbc` просто не собираются.
5. **Локаль `ru_RU.UTF-8`** — переводы интерфейса в комплекте FreePBX уже есть
   (`i18n/ru_RU/LC_MESSAGES/amp.mo`), но gettext без сгенерированной системной
   локали молча покажет английский.
6. **Удаление `extensions.ael`, `extensions.lua` и `index.html`** — примеры от
   `make samples` добавляли 20 контекстов `ael-*` и `dundi-*`, которых на бою
   нет, а `index.html` от Apache перекрывал корень сайта.

## Ограничения стенда

* **Один контейнер на всё** — MariaDB, Apache и Asterisk вместе. Для учебного
  стенда нормально, для чего-либо ещё — нет.
* **Звуковые подсказки Asterisk на английском.** Русские сообщения — это
  отдельный пакет звуков (`asterisk-core-sounds-ru`), он не связан с языком
  интерфейса. Для стенда не нужен; если захочется — добавляется через «Модули».
* **Очередь раздачи не создана.** Её удобнее сделать руками в интерфейсе:
  «Приложения → Очереди», номер 2929, участники — из списка выше. Это как раз
  тот случай, где полезно снять снимок до и после и посмотреть диff.
* **FreePBX перезаписывает конфиги**, поэтому он и не поднят «поверх» лабы:
  лаба живёт на руками написанном предсказуемом диалплане, и первый же «Apply
  Config» его затёр бы. Общий у них только базовый образ Asterisk.
