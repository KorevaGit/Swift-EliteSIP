# Настройки клиентов для лаборатории

Все данные — для стенда FreePBX 15 на Asterisk 13.38.3
(`docker-compose.freepbx.yml`), той же боевой версии Asterisk.

## Запуск

```bash
cd "/Users/koreva/Projects/Swift EliteSIP/Lab" && ./lab.sh up
```

Первый запуск на чистом томе — несколько минут, дальше секунды. Посмотреть
состояние: `./lab.sh status`. Остановить: `./lab.sh down`.

Наше приложение:

```bash
open -n "/Users/koreva/Library/Developer/Xcode/DerivedData/EliteSIP-gxdtafckxnqnnvbztvtbzwzglupz/Build/Products/Debug/EliteSIP.app"
```

## Адрес сервера

| Откуда подключаемся | Адрес | Порт |
|---|---|---|
| С самого Mac | `127.0.0.1` | `5060` (UDP) / `5061` (TLS) |
| С телефона в той же сети | текущий адрес Mac | `5060` (UDP) / `5061` (TLS) |

Адрес Mac в сети меняется при переподключении к другому Wi-Fi. Текущий:

```bash
ipconfig getifaddr en0
```

Править конфиг руками не нужно: `./lab.sh up` и `./lab.sh sync` подставляют
туда текущий адрес сами, без пересоздания контейнера. Но знать, чем это
грозит, стоит — Asterisk ставит этот адрес в SDP, и по устаревшему звук уходит
в никуда в обе стороны. Симптом обманчивый: звонок устанавливается и
завершается штатно, а разговора нет.

Если сеть сменилась при поднятом стенде, достаточно `./lab.sh sync`.

## PortSIP на iPhone

| Поле в PortSIP | Значение |
|---|---|
| Username / User name | `101` |
| Password | `elite101` |
| SIP Domain / Domain | текущий адрес Mac (см. выше) |
| Outbound proxy | оставить пустым |
| SIP Server / Proxy port | `5060` |
| Transport | UDP |
| Display name | любое, например `iPhone` |
| Кодеки | оставить G.711 (PCMU/PCMA), остальное можно выключить |
| SRTP / шифрование | выключить — пир 101 работает по открытому UDP |

Телефон должен быть в той же сети Wi-Fi, что и Mac. Брандмауэр macOS выключен,
порты опубликованы на всех интерфейсах — дополнительно ничего открывать не нужно.

Если нужен второй телефон — есть пиры `102` (`elite102`) и `103` (`elite103`),
настройки те же.

## Что можно набрать

| Номер | Что происходит |
|---|---|
| `650` | эхо-тест: слышно себя, лучшая проверка звука |
| `601` | сервер проигрывает файл — проверка приёма без передачи |
| `602` | тон 1004 Гц |
| `603` | принимает DTMF и произносит цифры обратно |
| `100`–`103` | звонок другому клиенту |
| `8000` | конференция ConfBridge |
| `22998` | заглушка «горячей раздачи» |
| `600` | записываемый демо-звонок M1.6 (не эхо — отвечает, играет фразу и кладёт трубку) |

Позвонить с iPhone на Mac — набрать `100`. В обратную сторону — `101`. С M3
приложение входящие принимает: на экране появится плавающее окно, и каждый раз
в новом месте — это защита от кликеров по координатам.

Если в настройках включено подтверждение цифрой, вместо «Ответить» будет ряд
цифр, и принять вызов нужно той, что названа в подписи.

Проверить приём без окна, из консоли:

```bash
(cd Tools/sipcheck && swift run sipcheck --user 100 --password elite100 --duration 15 --answer)
```

## Если звука нет

**Сначала — одна команда, она закрывает самый частый случай:**

```bash
./lab.sh status
```

Смотреть на раздел «Адрес в SDP (externip)». Если там 127.0.0.1 — дальше можно
не искать, причина найдена, лечится `./lab.sh sync`.

### Ловушка петли: почему она стоит отдельного раздела

Свежесозданный контейнер получает `externip=127.0.0.1` (см.
`FREEPBX_EXTERNAL_ADDRESS` в compose), а `localnet` — только `127.0.0.0/8`.
Значит **всем**, кто пришёл не с петли, Asterisk объявляет в SDP «шлите медиа на
127.0.0.1».

И Mac, и телефон приходят в контейнер через публикацию портов Docker, то есть
для Asterisk оба выглядят одинаково — `172.20.0.1`, различаясь только портом.
Различить их он не может и выдаёт обоим один и тот же адрес. Дальше пути
расходятся:

* **клиенту на этом же Mac** `127.0.0.1:1020x` — это как раз опубликованный порт
  контейнера, и всё случайно работает;
* **телефону** `127.0.0.1` — это сам телефон. PortSIP шлёт RTP себе в петлю,
  Asterisk не получает от него ничего, и разговор выходит односторонним:
  телефон нас слышит, мы его — нет.

Симптом коварен ровно этой асимметрией: со стороны Mac всё исправно, эхо-тест
`650` проходит (там оба конца медиа — сам Asterisk), а звука нет только на
звонках между клиентами. `./lab.sh up` синхронизирует адрес сам, но
пересоздание контейнера руками (`docker compose up -d`) — нет, и после уборки
контейнеров стенд молча остаётся с петлёй. 3 августа 2026 на разбор этого ушло
два захода; теперь `./lab.sh status` предупреждает прямым текстом.

`sync` берёт адрес с `en0`. Если Mac сидит не на Wi-Fi, адрес не определится, и
команда об этом скажет.

### Если дело не в адресе

Смотреть надо со стороны сервера — он единственный видит обе половины:

```bash
docker exec elitesip-freepbx asterisk -rx 'sip show channelstats'
```

* нули в `Recv` — до Asterisk не доходит поток от клиента;
* нули в `Send` — Asterisk не отправляет, обычно потому что не понял, куда;
* цифры в обеих колонках — медиа-путь исправен, дело в самом клиенте.

Журнал нашего приложения — вкладка «Диагностика», там весь обмен SIP и форматы
звука. Из командной строки то же самое:

```bash
"/Users/koreva/Library/Developer/Xcode/DerivedData/EliteSIP-gxdtafckxnqnnvbztvtbzwzglupz/Build/Products/Debug/EliteSIP.app/Contents/MacOS/EliteSIP" --log-to-stderr
```
