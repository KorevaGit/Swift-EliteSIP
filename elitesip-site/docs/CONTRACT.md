# Контракт панели и приложения

Что панель кладёт наружу и что приложение оттуда читает. Решения, из которых
это выведено, — в [DECISIONS.md](DECISIONS.md); здесь форма.

Обе стороны пишутся отдельно и обновляются не одновременно, поэтому всё ниже
меняется только с версией формата, а не по месту.

## Два объекта в бакете

| Объект | Кто кладёт | Кто читает | Когда |
| --- | --- | --- | --- |
| `presets/current.json` | панель при выкладке | все машины | опрос раз в полчаса |
| `activations/<адрес>` | панель при выпуске ключа | одна машина, один раз | при активации |
| `taken/<адрес>` | Worker при выдаче пакета | панель | опрос раз в пять минут |
| `seen/<installation_id>` | Worker при выдаче файла | панель | опрос раз в пять минут |

Адрес пакета не назначается, а **выводится из ключа**: первые 16 байт
SHA-256 от `elitesip.activation.object.v1\x00` и канонического ключа, шестнадцатеричной
строкой. Поэтому его знают обе стороны, а сервер посередине не нужен.

Приставка `activations/` в этот расчёт не входит: она принадлежит раскладке
бакета, а приложению приезжает внутри адреса канала раздачи. Worker по ней
отличает запрос за пакетом от запроса за чем угодно ещё и не отдаёт наружу то,
о чём его не спрашивали.

## Worker перед бакетом

Между машинами и R2 стоит Worker — `worker/worker.js`. Он делает три вещи,
которых бакет сам не умеет, и не делает больше ничего.

**Пакет отдаётся один раз.** Прежде чем отдать, Worker столбит его за собой
условной записью `taken/<адрес>` — «создай, если такого объекта ещё нет». Кто
записал, тот и отдаёт; остальные получают `410`. Здесь и живёт одноразовость
ключа: до Worker'а она держалась на честном слове.

Порядок «сначала отметить, потом отдать» выбран сознательно вместе с его ценой:
оборвавшаяся закачка сжигает ключ. Выпустить новый стоит одного нажатия, а
сработавший дважды ключ стоит рабочего места.

**Машина сообщает о себе заголовками**, а не строкой запроса: адрес файла
предустановок обязан быть одним и тем же для всех, иначе кэш раздаёт его каждой
заново.

| Заголовок | Что |
| --- | --- |
| `X-EliteSIP-Installation` | `installation_id` из пакета активации |
| `X-EliteSIP-App` | версия приложения |
| `X-EliteSIP-Schema` | версия схемы `AppSettings` |
| `X-EliteSIP-Revision` | применённая ревизия предустановки |

**Отметки.** `taken/<адрес>` ставится один раз и больше не меняется;
`seen/<installation_id>` перезаписывается при каждом заходе машины — это
состояние, а не череда событий.

```json
{ "format": 1, "installation_id": "8f2c…", "last_seen_at": "2026-08-24T15:30:00Z",
  "app_version": "0.1.25", "schema_version": 2, "preset_revision": 12 }
```

Состояние Worker'а лежит в самом бакете, а не в D1 или KV. Причина не в
бережливости: панель ходит в R2 и так, по S3, — и разбирает отметки тем же
доступом, которым выкладывает. Отдельное хранилище означало бы второй канал со
вторым секретом, то есть второе место, где можно ошибиться с доступом.

**Идентификатор, которого нет в базе, панель пропускает молча.** Машина
удалённого сотрудника продолжает тянуть файл: она о людях ничего не знает, а
файл лежит на R2.

## Пакет активации

Двоичный: `ESIPA1` — двенадцать байт nonce — AES-256-GCM. Заголовок идёт в
дополнительные данные, ключ выводится PBKDF2-HMAC-SHA256 со 150 000 итераций;
соль — первые 16 байт SHA-256 от `elitesip.activation.salt.v1\x00` и ключа.

Внутри — JSON:

```json
{
  "format": 1,
  "installation_id": "8f2c…",
  "issued_at": "2026-08-24T12:00:00Z",
  "employee": "Пётр",
  "number": "172",
  "sip_password": "…",
  "admin_password": "…",
  "preset": {
    "id": "6D1F5A20-…",
    "name": "Менеджер",
    "revision": 12,
    "schema_version": 2,
    "settings": { … }
  }
}
```

`installation_id` машина сохраняет навсегда и сообщает при каждом запросе за
файлом предустановок — это единственное, по чему панель узнаёт рабочие места.

`admin_password` лежит отдельным полем, а не внутри `settings`: `SettingsPreset`
вычищает блок доступа намеренно, и ломать это ради одного поля нельзя.

## Файл предустановок

```json
{
  "payload": "<байты JSON>",
  "signature": "<Ed25519>"
}
```

Подпись считается по байтам `payload`, и проверять её надо до разбора: так
проверка не зависит ни от канонизации JSON, ни от того, как посредник
переставит ключи. Внутри `payload`:

```json
{
  "format": 1,
  "generated_at": "2026-08-24T15:30:00Z",
  "presets": [
    { "id": "6D1F5A20-…", "name": "Менеджер", "revision": 12,
      "schema_version": 2, "fields": { … } }
  ]
}
```

**Машина ищет себя по `id`, а не по имени.** Имя переименовывают, и поиск по
нему разорвал бы связь у всех машин разом.

Один файл на все предустановки: машина не должна знать, сколько их всего, а
панель — держать список объектов в бакете в согласии с базой.

## Управляемые поля

`fields` и `preset.settings` — один и тот же объект. Он умышленно повторяет
Codable-представление типов приложения: `dtmf` — это `AppSettings.DTMFSettings`,
`incomingCall` — `CallGuardPolicy`, и так далее. Свой формат не притворялся бы
куском чужой модели, но потребовал бы на клиенте слоя перекладывания — а слой,
который перекладывает поля руками, однажды переложит не то.

| Ключ | Тип приложения | Что внутри |
| --- | --- | --- |
| `dtmf` | `AppSettings.DTMFSettings` | длительности, клавиши, раскладка сетки |
| `incomingCall` | `CallGuardPolicy` | защита приёма вызова |
| `queues` | `AppSettings.QueueDirectory` | словарь очередей |
| `conference` | `AppSettings.ConferenceSettings` | код конференции, добавочный комнаты |
| `portKnock` | `PortKnockSequence` | последовательность стука |
| `siteAddresses` | `SIPSiteAddresses` | пара адресов АТС |
| `acceptsAnyTLSCertificate` | поле профиля | доверие сертификату |

Здесь нет звука, рингтона, оформления, журналов, истории и рабочего места
профиля — это принадлежит машине.

**`acceptsAnyTLSCertificate` стоит полем верхнего уровня**, потому что в
приложении живёт внутри активного профиля, а не в `AppSettings`. Панель
управляет им ровно затем, чтобы держать его выключенным: аудит M7b нашёл
включённое ради лаборатории значение, молча оставшееся включённым на боевом
профиле.

**`isServerManaged` из `CallGuardPolicy` в файл не входит.** Приложение
выводит его из режима машины — «Предустановка» или «Вручную», — а приехавшее
поле означало бы два источника одного факта.

### Два правила разбора, зеркальные друг другу

- **Панель строга:** незнакомый ключ при сохранении ревизии — ошибка. Это
  единственное место, где опечатку в имени поля ещё можно показать человеку,
  вместо того чтобы разослать её на все машины обязательным обновлением.
- **Машина терпима:** незнакомое поле пропускается, понятное применяется. Она
  обязана работать со старой сборкой, и отказ от файла целиком означал бы, что
  до неё не доедет и смена адреса АТС, без которой она не звонит.

**Отсутствующий ключ и ключ со значением — разные вещи.** Отсутствие означает
«панель этим не управляет», и машина сохраняет своё текущее значение, а не
сбрасывает его в умолчание. Правило принято ещё в M8: иначе предустановка,
написанная ради макросов, молча стирала бы политику защиты.

### Пределы, которые панель проверяет

Взяты из приложения, а не придуманы: `DTMFSettings.maximumMacros` — 18,
`columnRange` — 1…4, `heightRange` — 44…96. Разойтись с ними значит выпустить
ревизию, которую машина приведёт к своим границам молча, и панель будет
показывать не то, что стоит на местах.

Сверх них панель ловит то, что синтаксически верно и бессмысленно по существу:
очередь с номером без названия, два адреса АТС, равные друг другу, требование
движения курсора с нулевым порогом, повтор стука раз в пять секунд.

## Версии

Их три, и путать их нельзя:

- **формат пакета активации** — `ESIPA1` в заголовке и `format` внутри;
- **формат файла предустановок** — `format` рядом с `generated_at`;
- **версия схемы `AppSettings`** — `schema_version` у каждой предустановки,
  совпадает с `AppSettings.currentSchemaVersion` (сейчас 2).

Первые две принадлежат этому контракту, третья — приложению. Машина сообщает
свою версию схемы при запросе за файлом, и панель показывает, кто отстал
настолько, что новые поля до него не доезжают.
