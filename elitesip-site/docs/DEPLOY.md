# Установка панели на сервер конторы

Поставлено 26 августа 2026 на `10.171.0.171`, Ubuntu 22.04.5, Docker 29.4.
Открывается по адресу **https://support.elitesip.vip** изнутри сети,
с настоящим сертификатом Let's Encrypt.

Это этап 6 из [PLAN.md](PLAN.md). Решение о том, почему панель стоит внутри, а
не на VPS, — в [DECISIONS.md](DECISIONS.md), раздел «Где что стоит».

## Наружу панель не смотрит

`support.elitesip.vip` разрешается в **10.171.0.171** — адрес частной сети.
Публичное имя, приватный адрес: снаружи по нему не достучаться вовсе, а внутри
не приходится диктовать цифры.

Проверить, что имя не уводит наружу, можно так — ответ должен быть адресом из
`10.`:

```
dig +short support.elitesip.vip
```

## Что где лежит

```
~/elitesip/
  docker-compose.yml   панель и Caddy
  Dockerfile.caddy     сборка Caddy с модулем DNS-Cloudflare
  Caddyfile            имя, TLS, перенаправление с адреса, журнал доступа
  .env                 доступы к R2 и токен DNS, права 600
  secrets/             ключ подписи и секрет сервера, 600, владелец 10001
  data/                panel.db, владелец 10001
  logs/caddy/          журнал доступа
```

**Владелец `data/` и `secrets/` — uid 10001, а не `ubuntuserver`.** Внутри
контейнера панель работает под непривилегированным пользователем с этим номером
(см. `Dockerfile`), и без `chown` она не открывает базу — падает с `unable to
open database file (14)` в бесконечном перезапуске. Прочитать секреты с сервера
можно только через `sudo`, и это правильно.

```
sudo chown -R 10001:10001 data secrets
sudo chmod 700 data secrets
```

## Первый администратор

Заводится **человеком**, на странице `/setup`, а не командой при установке:
пароль администратора не должен проходить через чужие руки и чужую историю
команд.

Если страница уже недоступна (администратор заведён), следующего добавляют так:

```
docker compose run --rm panel admin <имя>
```

Пароль читается со stdin — не аргументом: аргумент попадает в историю оболочки
и в список процессов.

## Ключ подписи: потеря необратима

`secrets/signing.key` — приватный ключ линии предустановок. Его открытая
половина вписана в `Config/Info.plist` приложения и уезжает в каждую сборку.

**Сменить ключ у настроенных машин нельзя.** Они перестанут принимать файл
предустановок, помашинный доступ и отзыв — то есть панель перестанет управлять
ими навсегда, и починить это можно будет только переустановкой приложения на
каждой машине руками.

Отсюда требование: **резервная копия в двух местах**, там же, где лежит ключ
Sparkle. Снять её:

```
sudo cat ~/elitesip/secrets/signing.key
```

Открытая половина выводится из приватной, поэтому отдельно её хранить не нужно:

```
{ printf "302e020100300506032b657004220420"; base64 -d secrets/signing.key | xxd -p -c 32; } \
  | xxd -r -p | openssl pkey -inform DER -pubout -outform DER | tail -c 32 | base64
```

Секрет сервера (`server.secret`) терять не так страшно: по нему считаются
отпечатки выданных ключей, и его потеря означает лишь, что найти активацию по
присланному ключу больше нельзя. Машин это не затрагивает.

## Доступы к R2

Сейчас панель ходит в бакет `elitesip-updates` **тем же ключом, которым
выкладываются выпуски** (`Config/publish.local.json` на машине разработчика).
Проверено, что ключ умеет всё, что панели нужно: `PUT`, `GET`, `LIST`,
`DELETE`.

**Это временно и стоит развести.** Ключ выкладки живёт на машине разработчика,
а панель — на сервере, где крутятся и чужие стеки; общий ключ означает, что
взлом сервера требует отзыва и того, чем выпускаются обновления. Отдельный
токен R2 заводится в Cloudflare (R2 → Manage API tokens, права Object Read &
Write на этот бакет) и подставляется в `.env` — это одна правка и перезапуск:

```
docker compose up -d --force-recreate panel
```

## Обновление панели

```
rsync -a --exclude .git --exclude data --exclude secrets --exclude .env \
  elitesip-site/ ubuntuserver@10.171.0.171:~/elitesip/
ssh ubuntuserver@10.171.0.171 'cd ~/elitesip && docker compose up -d --build'
```

Схема базы доводится до текущей версии при запуске сама. Откат бинарника на
старый рядом с новой базой панель **не** переживёт молча — она откажется
запускаться и скажет, какой версии схема.

## Бэкап

Забирать два каталога: `data/` (база) и `secrets/` (ключи). **Выгрузка обязана
шифроваться:** SIP-пароли лежат в базе открытым текстом — это записанный риск
номер 3 в [DECISIONS.md](DECISIONS.md).

## TLS: проверка DNS-01, а не HTTP-01

Сертификат выдан Let's Encrypt 26 августа 2026, продлевается сам.

Обычная проверка HTTP-01 здесь невозможна по построению: она требует, чтобы до
сервера достучались снаружи, а он стоит внутри сети и наружу не смотрит.
**DNS-01 доказывает владение именем записью в зоне** — до самого сервера ходить
не надо. Панель остаётся невидимой снаружи и получает при этом настоящий
сертификат, а не самоподписанный: браузер молчит, и никому не приходится
объяснять, почему предупреждение можно нажать «продолжить».

Модуль `caddy-dns/cloudflare` в стандартный образ не входит, поэтому Caddy
собирается из исходников — `Dockerfile.caddy`, около десяти минут на этом
сервере. Токен лежит в `.env` переменной `CF_API_TOKEN`, права — только правка
DNS зоны `elitesip.vip`.

Проверить, что отдаётся именно публичный сертификат:

```
curl -sv https://support.elitesip.vip/healthz 2>&1 | grep -E "issuer|expire date"
```

Ответ должен называть `Let'"'"'s Encrypt`. Если там `Caddy Local Authority` —
выпуск не прошёл, и Caddy подставил самоподписанный; причину видно в
`docker compose logs caddy`.

Обращение по голому адресу `10.171.0.171` перенаправляется на имя: на адрес
публичный сертификат не выдают, поэтому там стоит внутренний Caddy'"'"'s CA — и
именно поэтому по адресу ходить не надо, а надо по имени.

## Чего ещё нет

- **Проверка, что панель недоступна снаружи.** DNS указывает внутрь, но
  отдельно убедиться, что на периметре нет проброса 80-го порта на этот
  адрес, — за администратором сети.
- **Пароль учётной записи сервера.** На момент установки у `ubuntuserver` стоит
  `ubuntu`. На машине, где лежат SIP-пароли конторы и ключ подписи, это первое,
  что подберут. Сменить и перейти на вход по ключу.
