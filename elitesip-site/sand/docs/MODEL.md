# Песочница — модель данных и экраны

Выведено из [DECISIONS.md](DECISIONS.md). Здесь форма: таблицы, автомат
состояний, состав экранов. Отдельный файл базы `sand.db`; журнал действий не
здесь, а общий с панелью.

Времена — строки RFC 3339 в UTC, как в основной базе; показываются по Москве.

## Таблицы

### Песок

```
sandboxes
  id           INTEGER PRIMARY KEY
  rop          TEXT NOT NULL          -- фамилия РОПа
  format       TEXT NOT NULL          -- office | remote
  created_at   TEXT NOT NULL
  closed_at    TEXT                   -- закрыт администратором
  closed_by    INTEGER
```

Активный песок у РОПа один: частичный уникальный индекс по `rop`, где
`closed_at IS NULL`. Запрет живёт в базе, а не в форме, — иначе две вкладки его
обойдут.

### Работы по песку

```
sandbox_marks
  sandbox_id   INTEGER NOT NULL
  task         TEXT NOT NULL          -- ключ задачи из шаблона
  done_at      TEXT NOT NULL
  done_by      INTEGER NOT NULL       -- кто отметил
  PRIMARY KEY (sandbox_id, task)
```

Отметка — это строка. Снятая отметка — отсутствие строки, а не флаг: «кто и
когда» без факта выполнения смысла не имеет, а след остаётся в журнале.

### Пул номеров

```
sandbox_extensions
  sandbox_id   INTEGER NOT NULL
  number       TEXT NOT NULL
  employee_id  INTEGER                -- кому привязан, NULL пока свободен
  PRIMARY KEY (sandbox_id, number)
```

Уникальный индекс по `employee_id` (где не NULL): один номер — один человек.

### Сотрудники

```
sand_employees
  id           INTEGER PRIMARY KEY
  sandbox_id   INTEGER NOT NULL
  name         TEXT NOT NULL          -- ФИО как ввели
  bitrix_login TEXT
  bitrix_pass  TEXT
  bitrix_id    TEXT                   -- ID из Битрикса, руками
  outcome      TEXT                   -- hired | rejected, NULL пока идёт
  outcome_at   TEXT
```

`bitrix_id` уникален в пределах базы: один и тот же человек не может числиться
в двух песках.

Удаление строки разрешено только пока `bitrix_login` пуст, и только
администратору; после создания аккаунта человек уходит только исходом.

### Работы по сотруднику

```
employee_marks
  employee_id  INTEGER NOT NULL
  task         TEXT NOT NULL
  done_at      TEXT NOT NULL
  done_by      INTEGER NOT NULL
  PRIMARY KEY (employee_id, task)
```

### Сделки

```
sandbox_deals
  sandbox_id   INTEGER NOT NULL
  deal_id      TEXT NOT NULL
  employee_id  INTEGER                -- кому выдана, NULL пока в пуле
  given_at     TEXT
  PRIMARY KEY (sandbox_id, deal_id)
```

Выдача порции — одна транзакция: взять N свободных, проставить `employee_id`,
отдать CSV. Половина выданной порции при сбое невозможна.

### Комментарии

```
sandbox_comments
  id           INTEGER PRIMARY KEY
  sandbox_id   INTEGER NOT NULL
  author_id    INTEGER NOT NULL
  created_at   TEXT NOT NULL
  text         TEXT NOT NULL
```

Один пул на песок, к людям не привязан. Правки задним числом не делаем.

## Шаблон работ

Шаблон — не таблица, а код: список ключей с названием, разделом, инструкцией,
ссылками и зависимостями. Правка шаблона — правка кода, как и решено.

Ключи по песку: `rop`, `format`, `extensions`, `hardware`, `keys`, `libra`,
`seized`.

Ключи по сотруднику: `name`, `bitrix`, `libra`, `extension`, `base_filled`,
`inventory`, `outcome`, `base_drained`, `rusguard`.

Разделы для процента: аккаунты, телефония, доступы, база, техника, исход.
Процент считается по каждому разделу отдельно.

У удалённого песка `hardware`, `keys` и `inventory` заменяются на удалённую
настройку — тот же ключ, другое название и другая инструкция.

## Зависимости

Проверяются при отметке, в обе стороны:

| Нельзя отметить | Пока нет |
| --- | --- |
| `libra`, `base_filled`, `extension` | `bitrix` |
| `base_drained` | `base_filled` |
| `outcome` | `bitrix` |
| `seized` (песок) | `hardware` (песок) |

Обратное следование не спрашивается, а проставляется: отметка `outcome` при
пустом `bitrix` невозможна вовсе, поэтому «выведен ⇒ аккаунт создан» выполняется
само.

Снятие отметки, от которой зависят другие, снимает и их — с явным
предупреждением, сколько отметок уйдёт.

## Состояния песка

Вычисляются, руками ставится только последнее:

| Статус | Условие |
| --- | --- |
| начат | есть песок, есть хотя бы один сотрудник с ФИО |
| в процессе | заполнено что-либо сверх ФИО |
| завершён | все работы по песку и по всем сотрудникам выполнены |
| закрыт | `closed_at` не пуст |

Закрытие администратором доступно на любом статусе; запись в журнал отдельная,
причина не спрашивается.

## Экраны

| Адрес | Что |
| --- | --- |
| `/sandbox` | список активных песков: РОП, формат, людей, проценты по разделам, статус |
| `/sandbox/archive` | закрытые пески, фильтры по статусу, датам, формату, РОПу |
| `/sandbox/new` | создание: РОП, формат, пул номеров, загрузка CSV сделок |
| `/sandbox/{id}` | карточка: работы песка, таблица сотрудников, комментарии |
| `/sandbox/{id}/employee/{eid}` | карточка сотрудника: работы, ссылки, SQL для Libra, кнопки 300/100 |
| `/sandbox/template` | шаблон работ, только просмотр (правка — в коде) |

Маршрут `/sandbox` уже занят заглушкой (`showSandbox` в
`internal/web/handlers.go`) и уже стоит в шапке `base.html` с пометкой
«в разработке» — раздел заменяет заглушку, а не встаёт рядом.

Счётчики песочницы добавляются на общий обзор сайта. Колокол уведомлений —
общий для всех проектов, отдельная работа за рамками этого раздела.

## Обмен

* Выгрузка песка в CSV и XLSX.
* Создание песка из готовой таблицы Excel: колонки ФИО, логин, пароль, ID
  Битрикса, номер — всё необязательно, кроме ФИО.
* Порция сделок — CSV с заголовком `1, 2`, как ждёт импорт Битрикса.
