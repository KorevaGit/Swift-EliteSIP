# Worker перед бакетом

Стоит между машинами и R2 на `get.elitesip.vip`. Бакет приватный и наружу не
смотрит вовсе: другого пути к нему нет.

**Это тот же Worker, что раздаёт обновления с 20 августа 2026** (`M7h`), а не
второй рядом. Этап 5 панели его дополнил, и раздача обновлений осталась в
точности прежней: appcast, архивы выпусков, частичные запросы, сроки кэша.
Второй Worker означал бы второй хостнейм и вторую Basic-пару в бандле.

Сверх раздачи он делает три вещи, которых бакет сам не умеет:

1. отдаёт пакет активации **один раз** — здесь живёт одноразовость ключа;
2. оставляет отметку `taken/<адрес>` о том, что пакет забрали;
3. запоминает в `seen/<installation_id>`, какая машина, когда и на какой
   ревизии забирала файл предустановок.

Отметки наружу не раздаются: Basic-пара лежит в бандле каждого приложения, то
есть «внутри» её знают все машины, а перечень чужих `installation_id` им знать
незачем.

## Три вещи, которые нельзя трогать

Они не украшение — каждая ломает что-то живое:

- **`REALM` обязан оставаться `"restricted"`.** `URLSession` в macOS подставляет
  сохранённую Basic-пару только при точном совпадении realm; с другим значением
  приложение молча получит 401 и перестанет обновляться.
- **Частичные запросы.** Без них Sparkle не докачивает оборвавшуюся загрузку
  архива.
- **Пакет активации отдаётся с `no-store`.** Общее правило «всё, кроме `.xml`,
  неизменяемо на год» здесь дало бы прямо обратное нужному: закэшированная
  копия делает одноразовость бессмысленной.

Формат отметок и заголовков — [../docs/CONTRACT.md](../docs/CONTRACT.md),
раздел «Worker перед бакетом». Устройство и цена решений — в шапке `worker.js`.

Ни сборки, ни зависимостей: `main` в `wrangler.toml` указывает прямо на
исходник, и то, что лежит в репозитории, — ровно то, что выполняется в
Cloudflare.

## Состояние — в самом бакете

Ни D1, ни KV. Причина не в бережливости: панель ходит в R2 и так, по S3, — и
разбирает отметки тем же доступом, которым выкладывает. Отдельное хранилище
означало бы второй канал со вторым секретом, то есть второе место, где можно
ошибиться с доступом.

## Выкладка

```
CLOUDFLARE_API_TOKEN=... npx wrangler deploy
```

`AUTH_USER` и `AUTH_PASS` заданы секретами при первой выкладке канала обновлений
и **выкладку переживают** — задавать заново не нужно. Второго секрета для панели
нет намеренно: она к Worker'у не обращается вовсе, а читает отметки прямо из
бакета.

**Выкладка заканчивается отказом про `workers.dev` — это ожидаемо.** К этому
моменту скрипт уже загружен (строка `Uploaded elitesip-updates` выше отказа), а
маршрут `get.elitesip.vip` заведён отдельно и wrangler его не касается.
Прописать маршрут в `wrangler.toml` было бы чище, но для этого токену нужны
права на зону, а у выкладочного их нет — и не должно быть.

Проверить, что уехало именно новое:

```
curl -s -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  https://api.cloudflare.com/client/v4/accounts/<счёт>/workers/scripts/elitesip-updates \
  | grep -c TAKEN_PREFIX
```

## Откат

Прежние версии хранит сам Cloudflare:

```
npx wrangler rollback
```

Откатывать стоит при любом сомнении: этот Worker — единственный путь к
обновлениям для всех установленных копий.

## Проверка без Cloudflare

```
npx wrangler dev --local --port 8788
```

Бакет при этом местный. Положить в него объект и прочитать отметку:

```
npx wrangler r2 object put elitesip-updates/activations/<адрес> --file=пакет --local
npx wrangler r2 object get elitesip-updates/taken/<адрес> --local --pipe
```

`.dev.vars` рядом задаёт `BASIC_AUTH` для местного запуска и в репозиторий не
попадает.

**Что проверять в первую очередь — одноразовость.** Ради неё Worker и заведён:

```
for n in 1 2 3 4 5 6; do curl -s -o /dev/null -w "%{http_code} " -H "$A" \
  http://127.0.0.1:8788/activations/<адрес> & done; wait
```

Из шести одновременных запросов пакет обязан получить ровно один; остальные —
`410`. Если получили двое, условная запись не сработала, и одноразовости нет.
