# Перевод звонка

M5 добавляет перевод поверх установленного SIP-диалога. Сигнализация остаётся
в `SIPCore`, а приложение показывает оператору ход операции и не объявляет
успех раньше сервера.

## Слепой перевод

1. Оператор вводит номер и подтверждает перевод.
2. `SIPUserAgent` отправляет внутри текущего диалога `REFER` с
   `Refer-To: <sip:номер@домен>`.
3. Ответ `202 Accepted` означает только, что сервер начал операцию. В интерфейсе
   это состояние «Сервер переводит…», а не готовый перевод.
4. Asterisk сообщает судьбу созданного INVITE запросом `NOTIFY` с телом
   `message/sipfrag`.
5. Только финальный 2xx в sipfrag считается успехом. 404, 486 и другие отказы
   остаются разговором с исходным собеседником и показываются оператору
   человеческим текстом.

Каждый NOTIFY получает `200 OK`. Если сервер принял REFER, но за минуту не
сообщил результат, операция заканчивается явным таймаутом. Повторный перевод
того же диалога до финального результата локально запрещён.

`Subscription-State: terminated` завершает операцию сам по себе. Подписка
закрыта — значит, NOTIFY больше не придёт, и ждать минуту незачем: и пустое
тело, и оставшийся в нём промежуточный код читаются как «сервер завершил
перевод без результата». До аудита 30 июля 2026 года так разбиралось только
пустое тело, и NOTIFY с `100 Trying` при закрытой подписке вешал кнопку
перевода до таймаута.

Минута — значение по умолчанию параметра `transferResultTimeout` у
`SIPUserAgent`. Настраивается он только ради проверок: в бою остаётся
согласованная с заказчиком минута.

## Основа консультационного перевода

Протокольная основа уже есть: `SIPDialogIdentifier` строит значение
`Replaces`, а `SIPUserAgent.transfer(to:replacing:)` кодирует его как URI-header
в `Refer-To` по RFC 3891:

```text
Refer-To: <sip:602@pbx?Replaces=call-id%3Bto-tag%3Dremote%3Bfrom-tag%3Dlocal>
```

Полный пользовательский сценарий входит в M6 вместе с общей для перевода и
конференции многолинейной архитектурой. Хранение звонков будет переведено с
одного `activeCall` на три адресуемые линии. Тогда порядок будет таким:

1. исходная линия ставится на удержание;
2. на второй линии оператор звонит адресату и консультируется;
3. REFER уходит по исходному диалогу, а Replaces описывает консультационный;
4. при отказе обе линии остаются доступны, при успехе локальные ноги
   завершаются.

До появления адресуемых линий интерфейс предлагает только реально работающий
слепой перевод; неработающей кнопки консультации в нём намеренно нет.

## Что видит оператор

Строка состояния — единственный канал: журнала на панели нет.

| Событие | Строка |
|---|---|
| REFER отправлен | «Перевод…» |
| 202 Accepted | «Сервер переводит…» |
| NOTIFY с 2xx | «Переведён на 601», и она же остаётся после завершения нашей ноги |
| отказ, разговор жив | «Не переведён: занято» — человеческая причина из `describeCallFailure` |
| разговор кончился раньше результата | причина окончания звонка |

Последняя строка — не небрежность. BYE от Asterisk может обогнать финальный
NOTIFY, и тогда перевод, скорее всего, состоялся; объявлять в этом месте отказ
значило бы врать оператору о единственном, чего мы не знаем.

Номер перевода приложение чистит от пробелов до отправки: поле принимает
вставку из буфера, а номера копируют с разделителями. `SIPCore` такой номер
по-прежнему отклоняет — пробел в Request-URI ломает разбор, — но до него
доходит уже нормализованный.

## Проверки

`TransferTests` покрывают:

- REFER внутри исходного диалога;
- точный Refer-To слепого перевода;
- percent-encoding Replaces;
- успешный NOTIFY и обязательный ответ 200;
- отказ созданного INVITE;
- разбор первой строки `message/sipfrag`;
- закрытие подписки без финального кода;
- повтор REFER после вызова авторизации, с новым CSeq и свежим nonce;
- конец разговора во время перевода;
- таймаут ожидания NOTIFY.

Живого прогона против Asterisk 13.38.3 у перевода пока нет: всё выше проверено
сценарным сервером.
