# SRTP в EliteSIP

M2b защищает отдельный UDP-поток голоса. TLS шифрует только SIP-сигнализацию;
без SRTP содержимое RTP-пакетов осталось бы открытым.

## Профиль

Боевая связка Asterisk 13 + `chan_sip` использует SDES по RFC 4568:

- SDP объявляет `RTP/SAVP`;
- `a=crypto` предлагает `AES_CM_128_HMAC_SHA1_80`;
- 128-битный master key и 112-битный master salt передаются как 30 байт
  `inline:` внутри защищённого TLS-соединения;
- для каждого звонка генерируется новый ключ;
- стороны используют разные ключи для входящего и исходящего направлений.

При TLS SRTP обязателен. Ответ без `RTP/SAVP`, без поддерживаемого `a=crypto`
или с чужим tag отклоняется. Тихого перехода на открытый RTP нет. UDP-профиль
остаётся открытым только для лабораторной диагностики в Wireshark.

## Защита пакета

Из master key и salt выводятся три сеансовых ключа по RFC 3711: AES, HMAC и
session salt. RTP-заголовок остаётся открытым для маршрутизации, payload
шифруется AES-CTR, затем к пакету добавляется 80-битный HMAC-SHA1. В HMAC входит
rollover counter, поэтому переход 16-битного sequence number через ноль не
переиспользует поток шифрования.

Входящий пакет проходит HMAC и 64-пакетное replay window до расшифровки. Пакеты
с неверным тегом, слишком старые и повторные не доходят до RTP-парсера,
джиттер-буфера и динамиков.

## Проверка

Ключевая развёртка сверяется с официальным вектором приложения B.3 RFC 3711.
Отдельные тесты проверяют SDES, round-trip SRTP, подмену, replay, rollover и
запрет downgrade.

Живая проверка против точной боевой версии Asterisk:

```bash
cd Tools/sipcheck
swift run sipcheck \
  --user 200 --password elite200 \
  --transport tls --port 5071 --insecure-tls \
  --call 600 --duration 6
```

Ожидаемый итог: `согласовано: SRTP ...` и ненулевое число пакетов встречного
потока. `--insecure-tls` допустим только для самоподписанного сертификата
локальной лаборатории.

## Что проверено в ревизии

Реализацию писал другой исполнитель, поэтому она разобрана заново — построчно
против RFC 3711 и дополнительными тестами. Ошибок не нашлось; ниже то, что
именно сверено, чтобы не сверять второй раз.

**Криптография.** Вывод сессионных ключей совпадает с контрольными векторами из
приложения B.3 RFC 3711 — это самая сильная из возможных проверок, она ловит
любую ошибку в метках, выравнивании соли и длинах. Построение IV соответствует
§4.1.1: соль, XOR с SSRC в байтах 4–7 и с 48-битным индексом в байтах 8–13. Тег
считается по §4.2 над заголовком, шифрованной нагрузкой и ROC. Сравнение тега —
за постоянное время.

**Порядок операций.** Пакет сначала проверяется на подлинность и только потом
расшифровывается, так что неподлинные данные не доходят ни до RTP-парсера, ни до
аудиотракта. Оценка индекса, которая по необходимости читает заголовок до
проверки тега, состояние не меняет — иначе поддельными пакетами можно было бы
сбить счётчик оборотов и оглушить разговор, не зная ключа.

**Переход счётчика через ноль.** Место, которое ломается позже всего: номер
шестнадцатибитный, при 20 мс на пакет граница наступает через двадцать две
минуты разговора. К имевшимся тестам добавлен набор `SRTPRolloverTests`: потеря
пакета ровно на границе, опоздавший пакет из прошлого оборота уже после перехода,
двести пакетов насквозь через границу, повтор через границу, перестановка на
сорок пакетов и пакет старше окна. Всё проходит.

**Согласование.** Тихого понижения защиты нет: предложение `RTP/SAVP` требует
такого же ответа, иначе звонок завершается ошибкой. Тег и профиль в ответе
сверяются с предложенными. Разбор `a=crypto` намеренно строгий — строка с
lifetime, MKI или любыми session parameters отвергается целиком, а не
игнорируется частично: принять её значило бы согласиться на семантику, которой
контекст не выполняет.

**Ключи не утекают.** Тела SDP нигде не логируются, а `Data` в Swift печатается
как «30 bytes», поэтому ключ не попадает в журнал даже при отладочной печати
структур. Мастер-ключ генерируется заново на каждое предложение. Тело INVITE
переиспользуется при повторе с авторизацией — то есть сервер и мы работаем с
одним ключом, а не с двумя разными.

**Потоки.** Оба контекста живут на очереди `RTPSession`: исходящий трогается
только при отправке, входящий только при приёме. Параллельного доступа нет, и
`@unchecked Sendable` здесь честен.

## Чего не хватает: SRTCP

Отчёты RTCP по RFC 3711 §3.4 должны идти как SRTCP — со своим набором ключей
(метки вывода 3, 4, 5 вместо 0, 1, 2), собственным индексом и обязательной
аутентификацией. Этого нет.

Поэтому на защищённом потоке RTCP **выключен намеренно**, и движок говорит об
этом в журнал. Отправлять открытые отчёты рядом с шифрованным звуком нельзя:
собеседник их всё равно отбросит, а наружу уйдут SSRC, счётчики пакетов и
тайминги разговора, который мы только что взялись прятать.

Практическое следствие: на TLS-профиле не видно, как нас слышит собеседник —
ни потерь, ни джиттера, ни времени кругового обхода. Для боевого профиля это
и есть основной аргумент дописать SRTCP: ключи выводятся из того же мастер-ключа,
что уже есть, менять надо метки и завести отдельный счётчик индекса.
