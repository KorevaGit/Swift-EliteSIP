# Выпуск: подпись, нотарификация и Gatekeeper

Разбор для M7e и M7f. Написан по фактам нашей сборки, а не по общим статьям:
всё, что ниже проверено на текущем Release-бандле командами, которые здесь же и
приведены.

## Что именно блокирует Gatekeeper

Gatekeeper проверяет не всякий файл, а помеченный карантином — расширенным
атрибутом `com.apple.quarantine`. Его ставит тот, кто принёс файл извне: Safari,
почтовый клиент, AirDrop, архиватор при распаковке. Скопированное `scp`, `rsync`
или с флешки через терминал карантина обычно не несёт, и такое приложение
запускается даже неподписанным.

Отсюда первый вывод, важный для планирования: **работает ли Gatekeeper, решает
способ раздачи, а не приложение.** Если рабочие места разворачивает админ
скриптом, он может годами не встречать проблемы — до первого сотрудника,
которому DMG прислали ссылкой. Строить на этом раздачу нельзя: это не
конфигурация, а везение.

Начиная с macOS 10.15 приложение, подписанное Developer ID, обязано быть ещё и
нотарифицировано. Наша нижняя планка — ровно 10.15, то есть требование
действует на весь поддерживаемый диапазон. Не нотарифицированное приложение
Catalina показывает как «разработчика невозможно проверить» и открыть не даёт.
Обход через контекстное меню «Открыть» существует, но инструктировать им
операторов — значит приучать их снимать защиту с непонятных файлов; для
софтфона, который слушает сеть и держит пароли в связке ключей, это плохой урок.

## Что в проекте уже сделано

- **Hardened Runtime включён** и в Release действительно применяется. Проверено:
  `codesign -dvvv` на Release-бандле показывает `flags=0x10002(adhoc,runtime)`.
  В Debug Xcode его снимает («Disabling hardened runtime with ad-hoc
  codesigning»), поэтому первый настоящий прогон с ним — это Release.
- **Права заданы точечно.** В `Config/EliteSIP.entitlements` только микрофон
  (`com.apple.security.device.audio-input`); App Sandbox выключен осознанно и с
  объяснением прямо в файле.
- **`NSMicrophoneUsageDescription` на месте** — без него запрос доступа к
  микрофону не появится, а приложение просто молча не получит звук.
- **Бандл universal с нужными планками**: `x86_64` minos 10.15, `arm64` minos
  11.0, `libswift_Concurrency` вложен. Держит `Tools/check-compat.sh`.

## Что сломало бы нотарификацию — и что с этим сделано

Три находки на Release-бандле от 3 августа 2026. Все три — конфигурация, а не
код, но узнать о них в день выпуска было бы дорого. Ниже каждая с тем, чем она
закрыта в M7e 18 августа 2026.

**1. В Release попадал `com.apple.security.get-task-allow`. Закрыто настройкой.**

```bash
codesign -d --entitlements - <путь к EliteSIP.app>
```

показывал его рядом с микрофоном. Это отладочное право, разрешающее
присоединять отладчик; служба нотарификации отклоняет бинарь с ним. Появлялось
оно из-за ad-hoc подписи (`CODE_SIGN_IDENTITY = "-"`): Xcode добавляет базовые
права для разработки.

В Release выставлено `CODE_SIGN_INJECT_BASE_ENTITLEMENTS = NO`, и права свелись
к одному микрофону — проверено той же командой на ad-hoc сборке, то есть в
худшем случае. Надеяться, что «с настоящим Developer ID его не будет», не
пришлось: настройка убирает право независимо от того, чем подписано. Проверка
стоит и в `Tools/check-compat.sh`, и в `Tools/release.sh` — настройка невидимая,
а пропажу её иначе заметит служба Apple в день выпуска.

**2. Вложенный `libswift_Concurrency.dylib` подписан без Hardened Runtime. Закрыто скриптом выпуска.**

```bash
codesign -dvv <...>/EliteSIP.app/Contents/Frameworks/libswift_Concurrency.dylib
```

даёт `flags=0x2(adhoc)` — флага `runtime` нет. Нотарификация требует Hardened
Runtime у **всего** исполняемого содержимого бандла, и это одна из самых частых
причин отказа. Библиотеку кладёт туда `CopySwiftLibs` ради обратного
развёртывания конкурентности на Catalina, то есть выкинуть её нельзя.

`Tools/release.sh` переподписывает всё вложенное тем же Developer ID с
`--options runtime --timestamp` **до** подписи бандла и после этого проверяет
флаг у каждого файла отдельно. Порядок обязателен: подпись бандла считает хеши
вложенного, и библиотека, переподписанная после бандла, ломает подпись целиком.

**3. Подпись ad-hoc, без Team ID и без метки времени. Осталась — учётки Apple
Developer пока нет.** `TeamIdentifier=not set`, `Signature=adhoc`. Для
нотарификации нужны Developer ID Application, `--options runtime` и
`--timestamp`: без защищённой метки времени подпись считается непроверяемой.

Это единственное, что в M7e не сделано, и сделать это кодом нельзя: сертификат
выдаёт Apple по платной учётной записи. `Tools/release.sh` требует сертификат,
Team ID и профиль `notarytool` первыми же строками и без них не собирает вовсе —
чтобы «выпуск» без подписи не случился по невнимательности.

## Локальная проверка на этой машине ничего не доказывает

```bash
spctl --status
```

на машине разработки отвечает `assessments disabled`. При выключенных проверках
`spctl -a -vv` отвечает `accepted` **чему угодно**, включая ad-hoc сборку, —
что и происходит сейчас. Любая проверка Gatekeeper обязана делаться либо после
`spctl --master-enable`, либо на другой машине. Иначе зелёный результат означает
только то, что проверки выключены.

Заодно карантин надо имитировать руками — сама сборка его не несёт:

```bash
xattr -w com.apple.quarantine "0081;00000000;Safari;" /путь/EliteSIP.app
```

## Пока нет учётной записи Apple: своя подпись

Учётной записи Apple Developer нет, Developer ID выдать некому, и обойти это
нельзя ничем: нотарификация возможна только по платной учётке. Но подпись и
нотарификация — это две разные вещи, и вторая недоступна, а первая доступна
вполне.

`Tools/make-selfsigned-cert.sh` заводит самоподписанный сертификат для подписи
кода в связке ключей входа. Ни учётной записи, ни оплаты, ни Apple для этого не
нужно; доверие ставится в пользовательском домене, без `sudo` и без системной
связки — сертификат нужен только этой машине для подписи своих же сборок.

**Чего это не даёт.** Gatekeeper с такой подписью не проходится. С macOS 10.15
приложение, принесённое извне с карантином, обязано быть ещё и нотарифицировано,
и самоподписанный сертификат к этому не приближает ни на шаг. Раздавать сборку
ссылкой по-прежнему нельзя — только `scp`, `rsync` или флешка через терминал,
либо снятие карантина на месте:

```bash
xattr -dr com.apple.quarantine /Applications/EliteSIP.app
```

**Что это даёт, и ради чего всё затеяно.** Постоянную личность приложения. У
ad-hoc подписи она меняется при каждой пересборке, а от подписи зависят два
системных механизма — связка ключей (ACL записи привязан к подписи, и
`SecItemCopyMatching` держит поток до ответа человека) и TCC, то есть доступ к
микрофону. С постоянным сертификатом и то и другое спрашивается один раз. Для
приёмки на живом железе (M7f) это важнее, чем кажется: иначе половина прогона
уходит на разбор того, что именно спросила система и почему. Ровно об этом
раздел «Почему подписью стоит заняться раньше приёмки» ниже — и эта половина
пользы доступна уже сейчас, без учётной записи.

Выпуск такой сборкой:

```bash
Tools/release.sh --self-signed --identity "EliteSIP Self-Signed" --bump patch
```

Скрипт в этом режиме не нотарифицирует и не штемпелюет, метку времени не просит
(она нужна только нотарификации и лишь ставит выпуск в зависимость от сети), а
образ называет с суффиксом `-nonotarized` — чтобы такой файл не уехал в раздачу
как настоящий выпуск. Все остальные проверки остаются на месте.

## Срезы раздаются порознь

По умолчанию `Tools/release.sh` собирает **две отдельные сборки** — `x86_64` и
`arm64`, каждая своим образом: `EliteSIP-0.1.1-x86_64.dmg` и
`EliteSIP-0.1.1-arm64.dmg`. Universal собирается по требованию,
`--arch universal`.

Причина простая: каждая отдельная сборка вдвое легче, и на рабочее место
приезжает только то, что там исполняется. Цена тоже простая и её надо знать —
**срез теперь выбирает человек, а не система.** Universal-бандл нельзя было
скачать «не тот»; отдельные — можно, и ошибка выйдет несимметричной:

- Intel-сборка на Apple Silicon **запустится** — через Rosetta, если он вообще
  установлен. Для софтфона это худший из исходов: не отказ, который заметят
  сразу, а тихо другая нагрузка и другая задержка звука.
- ARM-сборка на Intel просто не откроется, и это как раз честно.

Отсюда два следствия для раздачи. Имя среза стоит прямо в имени образа, а не в
описании рядом. И проверка бандла в скрипте требует, чтобы отдельная сборка была
именно отдельной: лишний срез — это вдвое больший образ, ради которого всё и
разделено.

Номер сборки у срезов одной версии общий: это одно приложение, собранное под две
машины, а не два разных выпуска.

Автообновлению (M7h) это добавит работы: appcast придётся раздавать по срезам,
потому что Sparkle сам выбирать между ними не умеет. Приложение свой срез знает,
так что решается это адресом канала, а не логикой обновления.

## Порядок выпуска

Делает `Tools/release.sh` целиком, одной командой:

```bash
Tools/release.sh --bump patch \
    --identity "Developer ID Application: … (TEAMID1234)" \
    --team TEAMID1234 \
    --notary-profile elitesip
```

Пока учётной записи нет — то же самое своей подписью, без шагов 8 и 9:

```bash
Tools/release.sh --self-signed --identity "EliteSIP Self-Signed" --bump patch
```

Ниже — что именно он делает по шагам. Порядок подписи снизу вверх обязателен:
подпись бандла считает хеши вложенного, и переподписанная после бандла
библиотека ломает подпись целиком.

1. **Предполётные проверки.** Сертификат есть в связке и он именно Developer ID
   Application; профиль `notarytool` заведён; `Config/provisioning.local.json`
   на месте; дерево без незакоммиченных правок. Всё это стоит до сборки не из
   аккуратности: сборка с тестами идёт минуты, и узнавать на восьмом шаге, что
   профиля нотарификации нет, дорого.
2. **Версия.** `--bump patch|minor|major` поднимает `MARKETING_VERSION`, номер
   сборки растёт всегда. Любой обрыв дальше возвращает файл версии на место:
   наполовину поднятый номер в рабочем дереве — это следующий выпуск с чужим
   номером.
3. **Тесты и совместимость** — `Tools/check-compat.sh` целиком (`--skip-checks`
   отключает).
4. **Сборка** Release в отдельный `derivedDataPath`, чтобы выпуск не зависел
   от содержимого общей DerivedData. Шаги 4–9 повторяются для каждого среза:
   по умолчанию это две отдельные сборки, `x86_64` и `arm64`.
5. **Подпись** снизу вверх: сперва всё вложенное, затем бандл — Developer ID
   Application, `--options runtime`, `--timestamp`, с нашими entitlements.
6. **Проверки подписи:** `codesign --verify --deep --strict`; в правах нет
   `get-task-allow`; у бандла и у каждого вложенного файла флаг `runtime`; в
   подписи наш Team ID и метка времени. Каждая из них — это отказ
   нотарификации, узнанный за секунду вместо часа ожидания вердикта Apple.
7. **Проверки бандла:** нужные срезы и только они, нижние планки 10.15 и 11.0,
   `libswift_Concurrency` вложен, `provisioning.json` в ресурсах, версия в
   `Info.plist` сходится с той, что выпускаем.
8. **Нотарификация приложения** (`notarytool submit --wait`) и `stapler staple`
   на приложение.
9. **DMG** с приложением и ярлыком `/Applications`, подпись образа,
   **нотарификация DMG**, `stapler staple` и `stapler validate` на образ.

Учётные данные нотарификации берутся из профиля связки ключей
(`notarytool store-credentials`), а не из командной строки: `ps` видно всем, а
история оболочки переживает выпуск.

**Отправок на нотарификацию две, и обе нужны.** Билет прикрепляется к тому
файлу, который отправляли: степлинг DMG не кладёт билет внутрь приложения. А
приложение переживает свой образ — его копируют, переносят, восстанавливают из
архива, и на новой машине оно оказывается уже без DMG.

После скрипта остаётся ровно две вещи руками: закоммитить `Version.xcconfig` с
меткой версии и проверить образ на чистой машине с включёнными проверками —
скрипт об этом и напоминает последним экраном.

**Степлинг обязателен, а не желателен.** Без прикреплённого билета Gatekeeper
ходит к Apple по сети при первом запуске. Удалённые сотрудники работают через
L2TP VPN, и что там с исходящим доступом к серверам Apple — неизвестно; на
машине без ответа от Apple первый запуск в лучшем случае задумается, в худшем
не состоится.

## Версия живёт в одном файле

`Config/Version.xcconfig` — единственное место, где стоят `MARKETING_VERSION` и
`CURRENT_PROJECT_VERSION`; из конфигураций цели они убраны, иначе перекрывали бы
файл. Раньше номер стоял в двух конфигурациях сразу и поднимать его надо было
руками в обеих — то есть в конце концов не поднимался.

Две сборки с одним номером — это жалоба, которую не по чему разбирать: оператор
называет «0.1.0», а какой именно 0.1.0 у него стоит, не знает никто.
Автообновлению (M7h) номер нужен жёстче — как основание решения «обновлять или
нет», а не как подпись в «О программе». Поэтому номер сборки растёт при каждом
выпуске и никогда не убывает, даже когда человеческая версия та же.

## Секреты попадают в бандл шагом сборки

Административный пароль и код восстановления лежат в
`Config/provisioning.local.json` — вне Git. В бандл их кладёт фаза
«Провижининг» (`Tools/embed-provisioning.sh`), и правило у неё одно:

- **Release без файла роняет сборку.** Не подставляет умолчание, не пишет
  предупреждение — падает с объяснением. Выпуск без пароля внешне рабочий, а
  каждая машина из него встаёт с «Управлением», открытым любому оператору;
  заметить это можно только на рабочем месте и только случайно. Проверяется не
  только наличие файла, но и что он разбирается и что оба ключа непусты:
  недописанный файл декодируется в `nil` — то же самое, только незаметнее.
- **Debug не получает ничего.** В отладке `Provisioning` читает конфиг прямо из
  дерева проекта, поэтому отладочная сборка собирается и на машине, где файла
  нет вовсе, — включая CI.

Обе ветки проверены 18 августа 2026: Release без файла падает с внятной
ошибкой, Debug без файла собирается, и `provisioning.json` в отладочном бандле
не появляется.

## Проверки на чужой машине

`.github/workflows/ci.yml` гоняет `Tools/check-compat.sh` на macOS-раннере при
каждом push и pull request в `dev` и `main`: сборка семи пакетов под оба среза,
их тесты, каталог символов, universal-сборка приложения и проверки бандла.
Смысл именно в чужой машине — на машине разработки собирается всё, потому что
там стоят нужные версии и лежат некоммитимые файлы.

Подписи и нотарификации в CI нет намеренно. Секреты выпуска — сертификат
Developer ID, профиль `notarytool`, ключ Sparkle — остаются на машине выпуска:
канал выпуска, доступный из облака, это канал доставки чего угодно сразу на все
рабочие места. Провижининг в CI подставляется заведомо ненастоящий, и собранное
там приложение никуда не раздаётся.

## Что проверять на приёмке (M7f)

1. Скачанный DMG на **чистой** машине с включённым Gatekeeper: открывается без
   предупреждений.
2. То же самое без сети — доказательство, что степлинг сработал.
3. `lipo -archs` на установленном приложении: оба среза на месте.
4. Микрофон под Hardened Runtime: запрос появляется, доступ выдаётся, звук идёт.
   В Debug этот путь не проверяется вообще — там Hardened Runtime снят.
5. Связка ключей: пароль профиля читается без повторного запроса разрешения
   после перезапуска.

## Почему подписью стоит заняться раньше приёмки

Дело не только в Gatekeeper. Стабильность подписи — это стабильность
идентичности приложения для двух системных механизмов:

- **Связка ключей.** ACL записи привязан к подписи. Сейчас после каждой
  пересборки подпись другая, macOS показывает запрос разрешения, а
  `SecItemCopyMatching` блокирует поток до ответа человека — грабли, из-за
  которых чтение пароля в проекте вынесено с главного потока и не делается при
  старте. С постоянным Developer ID это прекращается.
- **TCC (доступ к микрофону).** Разрешение выдаётся приложению как подписанной
  сущности. Пересборка с новой ad-hoc подписью — новое приложение с точки зрения
  TCC, то есть новый запрос.

То есть настоящая подпись убирает не только «не могу открыть на чужой машине»,
но и часть повседневной возни на своей.

## Подписей две, и они про разное

Автообновление решено делать через Sparkle (M7h в [ROADMAP.md](ROADMAP.md)), а у
него своя подпись. Путать её с подписью Apple нельзя: они защищают от разного и
теряются по-разному.

| | Developer ID + нотарификация | Ключ Sparkle (EdDSA) |
|---|---|---|
| Кто проверяет | macOS при первом запуске | наше приложение перед установкой обновления |
| Что доказывает | «это приложение выпустил зарегистрированный разработчик, и Apple его просмотрела» | «этот файл собрал тот же, кто собрал установленную версию» |
| Где живёт секрет | сертификат в связке ключей + учётка Apple Developer | закрытый ключ в связке ключей машины выпуска |
| Что если потерять | выпустить новый сертификат, старые сборки продолжают работать | обновления перестают приниматься установленными копиями |
| Что если утечёт | чужой может подписать своё приложение вашим именем | чужой может подменить обновление — если ещё и получит доступ к раздаче |

### Что такое ключ EdDSA на практике

Это пара чисел, связанных математически. Одно — **закрытый ключ** — существует в
единственном экземпляре и хранится у того, кто выпускает сборки. Второе —
**открытый ключ** — не секрет вовсе: он зашивается прямо в приложение, в
`Info.plist`, ключом `SUPublicEDKey`, и уезжает на все рабочие места вместе со
сборкой.

Свойство пары такое: закрытым ключом можно поставить на файл подпись, а открытым
— проверить, что подпись поставлена именно этим закрытым ключом. Обратно не
работает: имея открытый ключ, подделать подпись нельзя.

Порядок выпуска с этим выглядит так:

1. Один раз генерируется пара. Инструмент Sparkle кладёт закрытый ключ в связку
   ключей машины выпуска и печатает открытый — его надо вставить в `Info.plist`.
2. При каждом выпуске готовый DMG подписывается закрытым ключом. Получается
   короткая строка — она кладётся в appcast рядом со ссылкой на файл и его
   размером.
3. Приложение на рабочем месте скачивает файл, считает его подпись открытым
   ключом из своего `Info.plist` и сверяет со строкой из appcast. Не сошлось —
   обновление не ставится.

### Зачем это, если файл и так лежит на HTTPS

HTTPS доказывает, **с кем** вы говорите: сервер тот, за кого себя выдаёт, и
никто по дороге содержимое не подменил. Он ничего не говорит о том, **что**
именно на этом сервере лежит.

Ключ Sparkle закрывает ровно этот зазор. Если сайт взломали и подменили DMG, или
файл подсунули через хостинг, CDN или бэкап, — HTTPS будет исправен, а подпись
не сойдётся, и обновление не встанет. Для приложения, которое само себя
заменяет на всех рабочих местах сразу и без спроса оператора, это не
перестраховка: канал обновления без проверки подписи — это канал доставки чего
угодно.

Подпись Apple здесь не заменяет ключ Sparkle. Она доказывает, что приложение
выпустил зарегистрированный разработчик, но не то, что это **наше** приложение,
а не чужое, тоже подписанное и нотарифицированное.

### Что с ним делать по-хозяйски

- **Хранить.** Закрытый ключ лежит в связке ключей машины выпуска. Этого мало:
  умерший диск означает, что установленные копии перестанут принимать
  обновления навсегда. Нужна резервная копия там же, где хранятся остальные
  секреты выпуска, — вне этой машины.
- **Не класть в репозиторий.** Ни в каком виде, включая «временно, чтобы
  собрать». История Git не забывает.
- **Знать порядок смены.** Меняется ключ болезненно: сначала выпускается версия,
  которая доверяет новому ключу, и надо дождаться, пока на неё перейдут все
  рабочие места; только потом можно начинать подписывать новым. Пока хоть кто-то
  сидит на старой версии, выпускать надо обеими подписями или не менять ключ
  вовсе. Именно поэтому резервная копия важнее, чем кажется: потеря ключа
  чинится не сменой ключа, а обходом всех рабочих мест руками.
- **Открытый ключ секретом не считать.** Он и так в каждой копии приложения.
