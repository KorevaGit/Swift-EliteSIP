# Согласованный план EliteSIP

Актуализирован по ответам заказчика 29 июля 2026 года. Этот документ отделяет
уже реализованное поведение от продуктовой приёмки и следующих работ.

## Конфиденциальность конфигурации

Боевые адреса, номера и учётные данные не являются значениями по умолчанию
приложения и не хранятся в Git. Пароли живут только в Keychain. Остальные
боевые параметры должны приезжать из EliteDash либо вводиться администратором
в локальном режиме.

Для проверки предусмотрены два типа профиля:

- офисный профиль для локального Asterisk;
- удалённый профиль для внешнего адреса.

Оба фактически используют SIP/UDP на стандартном порту. До выпуска удалённого
профиля надо подтвердить, проходит ли он через VPN: без VPN сигнализация,
Digest challenge/response и RTP идут по сети открыто.

## Принятые продуктовые решения

### M0 — платформа и форма приложения

- Продукт остаётся только для macOS.
- Поддержка Intel Mac обязательна вплоть до macOS 10.15 Catalina.
- Современная сборка должна работать нативно на Apple Silicon и новых Intel
  Mac; текущий deployment target 14.0 нельзя считать окончательным.
- Панель остаётся компактной и не должна мешать работе менеджера.
- Настройки закрываются административным доступом.
- Добавляются несколько профилей SIP-аккаунтов, но зарегистрирован одновременно
  только один выбранный профиль.
- Добавляется история звонков.

### M1 — аккаунт и транспорт

- Боевой Asterisk сейчас настроен на UDP; UDP нельзя считать только
  лабораторным транспортом.
- Один активный профиль выбирается из нескольких сохранённых.
- Номер аккаунта используется одновременно как SIP username, отображаемое имя
  и локальная метка профиля. SIP dialog tag остаётся случайным протокольным
  значением и из номера не строится.
- Секрет хранится в Keychain отдельно для каждого профиля.
- Точные боевые значения не зашиваются в приложение и не коммитятся.
- TLS/SRTP остаются поддерживаемым профилем, но не считаются фактически
  развёрнутыми на бою до проверки конфигурации Asterisk.

### M1.5 — FreePBX и очередь

- Точная лабораторная пара остаётся FreePBX 15 + Asterisk 13.38.3 + `chan_sip`.
- Очередь 2929 и тестовые участники должны создаваться автоматически, чтобы
  поведение очереди входило в воспроизводимую end-to-end проверку.
- Пользовательский боевой контекст `from-auto-dialer` воспроизводится только по
  проверенному фрагменту боевого диалплана. Его нельзя угадывать по CDR/CEL.
- Рядом с конфигурацией нужен разбор потока: входящий канал, Local-пара,
  `MixMonitor`, `Queue`, плечо агента и возврат звонка.

### M1.6 — CDR, CEL и запись

- Запись разговоров на стороне FreePBX — реальное боевое требование.
- EliteDash должен получать полные CDR и CEL, а не только сокращённую
  телеметрию клиента.
- Срок хранения, права доступа и жизненный цикл записей остаются
  ответственностью боевого FreePBX.

### M2 — аудио

- G.722 предлагается первым; PCMU/PCMA остаются обязательным fallback через
  обычное согласование SDP.
- Раздельный выбор микрофона и выхода сохраняется.
- Для раздельных устройств планируется независимый DSP-слой подавления шума и
  эха, потому что VoiceProcessingIO не работает с приватным агрегатным
  устройством. Конкретный алгоритм выбирается после замеров задержки, качества,
  нагрузки на старых Intel Mac и проверки лицензии.
- Автоматическое усиление по умолчанию выключается и остаётся пользовательской
  или административной опцией.
- M2 функционально реализован, но эксплуатационная приёмка продолжается:
  новые устройства, старые Intel Mac, длинные разговоры, переключение
  устройств и работа через колонки входят в матрицу ручных проверок.

### M2b — защита и RTCP

- На боевом Asterisk RTCP выключен; отсутствие SRTCP сейчас не блокирует
  существующий боевой сценарий.
- Профиль SDES нельзя считать подтверждённым без выгрузки фактических настроек
  Asterisk и живой проверки.
- Главный открытый риск — UDP удалённого профиля. Надо подтвердить наличие VPN
  или принять и документировать открытый транспорт.
- Для удалённой работы используется L2TP VPN. Отдельный скрипт подключения
  должен быть проверен именно как часть VPN-маршрута: простая отправка исходящих
  пакетов может открыть NAT, но сама по себе не шифрует SIP/RTP.

### M3 — входящий вызов и CallGuard

- Окно показывает имя extension. После синхронизации EliteDash может прислать
  понятный псевдоним, который заменит техническое имя.
- Политикой защиты управляет EliteDash. Если синхронизация выключена, доступен
  специальный локальный режим под паролем администратора.
- Случайная задержка активации удаляется. Кнопка активна сразу.
- Основная защита по умолчанию — случайная позиция окна.
- Цифровое подтверждение по умолчанию выключено.
- Клавиатурный ответ пока не входит в реализацию: в текущем парке колл-центра
  нет Mac. К вопросу можно вернуться после появления такого рабочего места.
- Средства доступности и локальное удалённое управление на рабочих местах не
  используются. EliteDash управляет настройками и получает логи, но не
  синтезирует клики в окно вызова.
- Отказ оператора отвечает `486 Busy Here`, чтобы очередь могла продолжить
  раздачу.

### M4 — hold, DTMF и макросы

- Текущий формат макроса сохраняется до появления боевых корректировок.
- Основной источник макросов — EliteDash; резервный источник — администратор в
  локальном режиме.
- Типично ожидается около восьми макросов, но жёсткого лимита нет.
- Менеджер может менять представление сетки, не меняя защищённое содержимое
  макросов.
- Текущие длительности тонов и пауз пока сохраняются.
- Если `telephone-event` не согласован, DTMF остаётся недоступным. SIP INFO не
  добавляется без подтверждённой необходимости.
- Серверное удержание должно пройти живую end-to-end проверку.

### M5 — перевод

- Слепой перевод разрешается и на внутренние, и на внешние цели, если это
  разрешает диалплан Asterisk.
- При отказе исходный разговор сохраняется, интерфейс возвращается к нему и
  показывает понятную причину: занято, нет ответа, номер не существует или
  сервер не сообщил результат.
- Таймаут ожидания результата REFER остаётся 60 секунд.
- Сценарии бота и автоматического возврата в колл-центр надо классифицировать
  по SIP-трассе: серверная Queue/Dial-логика и входящий REFER требуют разной
  реализации клиента.

### M6 — линии и конференция

- Боевой feature-code конференции не угадывается; нужен проверенный фрагмент
  `features.conf` и связанного диалплана.
- Пользователю показываются состояния обычным языком, без терминов DTMF,
  REFER, NOTIFY и ConfBridge.
- Модель комнат и возможность повторить команду после неподтверждённой попытки
  согласуются после разбора боевого диалплана.

### M6b — жизненный цикл

- Отключение SIP-профиля недоступно во время активного звонка.
- Mute продолжает отправлять корректно закодированную тишину.
- Удержание продолжает принимать серверную музыку ожидания.
- При удержании ради перевода и во время дозвона клиенту проигрывается
  серверная рекламная вставка. Клиент не должен перекрывать или локально
  генерировать её.
- Перед многолинейным UI выполняется живой прогон параллельных линий и
  резерваций RTP/RTCP.

## Следующие этапы

### Коррекция M3 перед продолжением M6

1. Убрать задержку активации из действующей политики и интерфейса.
2. Сохранить миграцию старого файла настроек без молчаливого возврата задержки.
3. Обновить отчёт CallGuard: ранний клик больше не является нарушением.
4. Удалить текущий локальный перехват цифр из обязательного пользовательского
   сценария; глобальный клавиатурный ответ пока не реализовывать.

### Завершение M6

1. Три адресуемые линии.
2. Одна активная аудиолиния, остальные на удержании.
3. Консультационный перевод через REFER/Replaces.
4. Серверная конференция после сверки боевого диалплана.
5. Живой прогон параллельных линий.

### M7 — совместимость, локальное администрирование и выпуск

Выпускается один продукт:

- **EliteSIP Universal** — `arm64 + x86_64`;
- срез `x86_64` поддерживает macOS 10.15 Catalina и новее;
- срез `arm64` поддерживает macOS 11 Big Sur и новее.

Отдельный Legacy-target не нужен: Catalina уже содержит SwiftUI,
Network.framework и CryptoKit. Нужен один слой обратной совместимости для API,
добавленных после Catalina.

Пробная x86_64-сборка с deployment target 10.15 уже дошла до общих пакетов.
Первый подтверждённый блокер — `Duration` и `ContinuousClock` в CallGuard,
доступные только с macOS 13. Удаление задержки активации уменьшит объём этой
переделки, но время событий для телеметрии всё равно надо перевести на
совместимое представление.

Работы:

1. Снизить platform declarations трёх Swift-пакетов и deployment target
   приложения до Catalina.
2. Заменить `Duration`/`ContinuousClock` совместимым монотонным временем.
3. Заменить Observation `@Observable` на модель, совместимую с Catalina
   (`ObservableObject`/явные уведомления).
4. Заменить SwiftUI `App`/`Window` lifecycle на совместимый с Catalina
   `NSApplicationDelegate`, продолжая показывать общие SwiftUI-вью через
   `NSHostingController`.
5. Проверить каждое используемое SwiftUI API и дать AppKit fallback только
   отдельным новым оконным функциям, отсутствующим в Catalina.
6. Проверить обратное развёртывание Swift concurrency на реальном Mac.
7. Проверить CoreAudio, VoiceProcessingIO, Keychain и DSP на реальном Intel Mac
   с Catalina.
8. Настроить Release-сборку `arm64 + x86_64`, подпись, нотарификацию и один DMG.
9. Автоматически проверять обе архитектуры и отдельную x86_64-сборку с target
   10.15.
10. Добавить профили нескольких аккаунтов с одним активным.
11. Добавить пароль администратора и специальный локальный режим.
12. Добавить локальную историю звонков с устойчивой схемой хранения.
13. Выключить AGC по умолчанию.
14. Исследовать и внедрить отдельный DSP шумоподавления/эхоподавления.
15. Добавить файловые логи.

### M8 — EliteDash

1. Централизованная политика CallGuard.
2. Псевдонимы extension для входящего окна.
3. Макросы и их раскладка.
4. Полные CDR/CEL и объединённая история звонков.
5. Телеметрия CallGuard.
6. Управляемые профили аккаунтов без передачи паролей через Git.
7. Провижининг удалённых сотрудников.

## Нужны ответы

1. Самая старая точная модель Intel Mac и объём её памяти для оценки нагрузки
   universal x86_64-среза и отдельного аудио-DSP.
2. Что именно делает скрипт удалённого подключения: поднимает L2TP/маршруты или
   только периодически отправляет пакеты для NAT.
3. SIP-трасса либо диалплан автоматического возврата клиента в колл-центр.
4. Боевые фрагменты `from-auto-dialer`, `features.conf` и связанного контекста
   без паролей и персональных данных.
5. Рекламная вставка формируется Asterisk для клиента или должна звучать также
   менеджеру.
